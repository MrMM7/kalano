## 1. Overview

This specification defines the core authentication dependency (`get_current_user`) and the profile endpoint (`GET /api/v1/auth/me`) for the Kalano multi-vendor e-commerce platform.

In Kalano, authentication is stateless and token-based using JSON Web Tokens (JWT). Per the Kalano Constitution:
- Authentication does not use Supabase Auth; tokens are generated by FastAPI upon login and signed with an HMAC secret (§4.2).
- The primary storage and transport mechanism for JWTs is an **httpOnly cookie** named `kalano_token` (§4.2).
- To support developer tooling (OpenAPI `/docs`, automated API testing, CLI tools, and non-browser clients), this specification also supports an `Authorization: Bearer <token>` header as a secondary fallback.
- The `get_current_user` dependency serves as the universal authentication gatekeeper for all protected endpoints across the application (e.g., cart, checkout, order history, merchant dashboard, logistics operations).
- The `GET /api/v1/auth/me` endpoint allows authenticated clients (specifically the Next.js `AuthContext` on initial application mount) to retrieve the profile of the current user.
- Any unauthorized access (missing token, invalid token signature, expired token, or user deleted from the database) results in an HTTP `401 Unauthorized` response conforming to the platform's standard error envelope (§4.4).

## 3. Functional Requirements

### 3.1 — Token Extraction Strategy (Cookie with Header Fallback)

The `get_current_user` dependency must extract the JWT access token from the incoming HTTP request using the following priority order:

1. **httpOnly Cookie (Primary)**: Check the request cookies for a cookie named `kalano_token` (`request.cookies.get("kalano_token")`).
2. **Authorization Header (Fallback)**: If `kalano_token` is missing or empty, check the `Authorization` request header (`request.headers.get("Authorization")`).
   - If the header exists and starts with the prefix `"Bearer "`, strip the prefix and extract the token string.
   - If the header is malformed (e.g., does not start with `"Bearer "` or contains no token), treat the token as missing.
3. **Missing Token Handling**: If neither the cookie nor the header yields a token string, the dependency must immediately abort by raising an HTTP `401 Unauthorized` exception with error code `MISSING_TOKEN` and message `"Authentication required."`.

### 3.2 — Token Decoding and Cryptographic Verification

- The backend must provide a helper function `decode_access_token(token: str) -> dict | None` located in `backend/app/utils/jwt.py`.
- Decoding must be performed using `jose.jwt.decode`:
  - Secret key: `settings.jwt_secret_key`.
  - Allowed algorithms: `[settings.jwt_algorithm]` (default: `HS256`).
- The decoding operation verifies:
  - The HMAC-SHA256 signature against the configured `jwt_secret_key`.
  - The token expiration timestamp (`exp` claim) against the current UTC timestamp.
- If the token signature is invalid, the token is malformed, or the token has expired:
  - `jose.exceptions.ExpiredSignatureError` or `jose.exceptions.JWTError` is caught.
  - `decode_access_token` returns `None`.
- If decoding succeeds, `decode_access_token` returns the payload claims dictionary (containing `user_id`, `user_role`, and `exp`).
- If `decode_access_token` returns `None`, or if the payload lacks a valid `user_id` claim, `get_current_user` must raise an HTTP `401 Unauthorized` exception with error code `INVALID_TOKEN` and message `"Token is invalid or expired."`.

### 3.3 — Database User Resolution

- Using the `user_id` extracted from the verified token payload, the dependency queries the Supabase `users` table using `get_supabase_client()`:
  ```python
  client = get_supabase_client()
  result = client.table("users").select("*").eq("id", user_id).execute()
  ```
- If the database returns no matching record (`not result.data`), the user has been deleted or deactivated after token issuance.
  - The dependency must raise an HTTP `401 Unauthorized` exception with error code `USER_NOT_FOUND` and message `"User no longer exists."`.
- If the record is found, `get_current_user` returns the user dictionary (`result.data[0]`), which includes all database columns (`id`, `created_at`, `email`, `display_name`, `user_role`, `address`, `password_hash`).

### 3.4 — Current User Endpoint (`GET /api/v1/auth/me`)

- Route path: `/api/v1/auth/me`.
- HTTP Method: `GET`.
- Operation tag: `["Auth"]`.
- Route dependency: `Depends(get_current_user)`.
- Behavior:
  - Receives the resolved user dictionary from `get_current_user`.
  - Constructs and returns a `UserResponse` Pydantic model (`UserResponse(**current_user)`).
  - Serializes to HTTP `200 OK`.
- **CRITICAL Security Invariant**: The `password_hash` column present in the database record MUST NEVER be returned to the client. `UserResponse` defines only safe public fields (`id`, `created_at`, `email`, `display_name`, `user_role`, `address`) and automatically omits `password_hash`.

### 3.5 — Standard Error Envelope

All authentication errors raised by `get_current_user` or `/api/v1/auth/me` must conform to the standard error envelope (§4.4):

```json
{
  "error": {
    "code": "<ERROR_CODE>",
    "message": "<HUMAN_READABLE_MESSAGE>"
  }
}
```

Standard authentication error codes:
| Error Code | HTTP Status | Trigger Condition |
|---|---|---|
| `MISSING_TOKEN` | `401 Unauthorized` | Neither `kalano_token` cookie nor `Authorization: Bearer <token>` header was provided. |
| `INVALID_TOKEN` | `401 Unauthorized` | Token is expired, signature is invalid, token string is malformed, or payload lacks `user_id`. |
| `USER_NOT_FOUND` | `401 Unauthorized` | Token is cryptographically valid, but the user ID is not found in the `users` table. |

## 4. Acceptance Criteria

- [ ] **AC1 — Cookie Authentication**: Sending a valid JWT in the `kalano_token` cookie to `GET /api/v1/auth/me` returns HTTP `200 OK` with the user profile in `UserResponse` format.
- [ ] **AC2 — Bearer Header Authentication**: Sending a valid JWT in the `Authorization: Bearer <token>` header returns HTTP `200 OK` with the user profile.
- [ ] **AC3 — Cookie Priority**: When both `kalano_token` cookie and `Authorization: Bearer` header are present in the request, the cookie is evaluated first.
- [ ] **AC4 — Missing Token Rejection**: A request without any cookie or `Authorization` header returns HTTP `401 Unauthorized` with error code `MISSING_TOKEN`.
- [ ] **AC5 — Expired Token Rejection**: A request with an expired JWT (expiration timestamp in the past) returns HTTP `401 Unauthorized` with error code `INVALID_TOKEN`.
- [ ] **AC6 — Invalid Signature Rejection**: A request with a JWT signed with an incorrect secret key or a corrupted token string returns HTTP `401 Unauthorized` with error code `INVALID_TOKEN`.
- [ ] **AC7 — Missing User ID Claim**: A request with a JWT that is syntactically valid but lacks a `user_id` claim returns HTTP `401 Unauthorized` with error code `INVALID_TOKEN`.
- [ ] **AC8 — User Not Found in Database**: A request with a valid JWT referencing a `user_id` that does not exist in the `users` table returns HTTP `401 Unauthorized` with error code `USER_NOT_FOUND`.
- [ ] **AC9 — Password Hash Exclusion**: The `password_hash` field is strictly omitted from the `GET /api/v1/auth/me` response body under all circumstances.
- [ ] **AC10 — Reusable Dependency**: The `get_current_user` function can be injected into any FastAPI route via `Depends(get_current_user)` and injects the user dictionary.
- [ ] **AC11 — OpenAPI Documentation**: The endpoint is registered at `/api/v1/auth/me` under tag `Auth` with summary, description, and documented 200/401 response models.

## 5. API Contract

### `GET /api/v1/auth/me`

**Summary**: Get current user profile  
**Description**: Returns the profile of the currently authenticated user. Requires a valid JWT access token provided in the httpOnly `kalano_token` cookie (preferred) or `Authorization: Bearer <token>` header (fallback).  
**Tags**: `["Auth"]`  

#### Request Headers & Cookies

| Location | Name | Type | Required | Description |
|---|---|---|---|---|
| Cookie | `kalano_token` | string | Optional* | The httpOnly JWT access token set on login |
| Header | `Authorization` | string | Optional* | Format: `Bearer <token>` |

*\* At least one valid authentication token must be provided via cookie or header.*

#### Success Response (`200 OK`)

```json
{
  "id": "e4b01e3e-7a42-4f1b-8c29-33b6d080b091",
  "created_at": "2026-09-03T12:00:00Z",
  "email": "buyer@example.com",
  "display_name": "Jane Doe",
  "user_role": "buyer",
  "address": null
}
```

| Field | Type | Description |
|---|---|---|
| `id` | UUID string | Unique user identifier |
| `created_at` | datetime (ISO 8601) | Account creation timestamp |
| `email` | string | User email address |
| `display_name` | string | User public display name |
| `user_role` | string | Account role (`"buyer"` or `"merchant"`) |
| `address` | string or null | User delivery/contact address |

#### Error Responses (`401 Unauthorized`)

**1. Missing Token**:
```json
{
  "error": {
    "code": "MISSING_TOKEN",
    "message": "Authentication required."
  }
}
```

**2. Invalid or Expired Token**:
```json
{
  "error": {
    "code": "INVALID_TOKEN",
    "message": "Token is invalid or expired."
  }
}
```

**3. User No Longer Exists**:
```json
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User no longer exists."
  }
}
```

## 6. UI/UX Requirements

This specification covers backend components: the `get_current_user` dependency and the `GET /api/v1/auth/me` endpoint.

### Frontend Integration Context

- In **Step 2.6 (`specs/006-auth-context-and-middleware/`)**, the Next.js application initializes an `AuthContext`.
- Upon initial mount, `AuthContext` executes:
  ```typescript
  fetch("/api/v1/auth/me", { credentials: "include" })
  ```
- If the response is `200 OK`, the user state is populated with `UserResponse`, marking the user as authenticated.
- If the response is `401 Unauthorized`, the user state is set to `null` (guest user), and any active protected route redirects to `/login`.

## 7. Edge Cases & Error Handling

| Scenario | Handling Strategy | Status Code & Error Code |
|---|---|---|
| Request contains neither cookie nor Authorization header | Detect absence in `get_current_user`; raise 401 | `401 Unauthorized` (`MISSING_TOKEN`) |
| Authorization header exists but does not start with `"Bearer "` (e.g. `"Basic dXNlcjpwYXNz"`) | Rejected by prefix check; treated as missing token | `401 Unauthorized` (`MISSING_TOKEN`) |
| Authorization header is `"Bearer "` with whitespace or no token | Stripped value is empty string; treated as missing token | `401 Unauthorized` (`MISSING_TOKEN`) |
| Cookie exists but contains empty string (`kalano_token=""`) | Evaluated as falsy; checks fallback header or raises 401 | `401 Unauthorized` (`MISSING_TOKEN`) |
| Token string is corrupt or malformed (not 3 period-separated base64 segments) | `jwt.decode` raises `JWTError`; caught and returns `None` | `401 Unauthorized` (`INVALID_TOKEN`) |
| Token signature does not match configured `jwt_secret_key` | `jwt.decode` raises `JWTError`; caught and returns `None` | `401 Unauthorized` (`INVALID_TOKEN`) |
| Token expiration timestamp (`exp`) has passed | `jwt.decode` raises `ExpiredSignatureError`; caught and returns `None` | `401 Unauthorized` (`INVALID_TOKEN`) |
| Token is valid but payload lacks `"user_id"` key | Validated in `get_current_user`; payload.get("user_id") is None | `401 Unauthorized` (`INVALID_TOKEN`) |
| `user_id` does not exist in `users` table (e.g., account deleted) | Supabase returns empty query list `[]` | `401 Unauthorized` (`USER_NOT_FOUND`) |
| Both cookie and Bearer header are provided, but cookie is invalid and header is valid | The cookie is checked first; because cookie is present, it is evaluated and rejected | `401 Unauthorized` (`INVALID_TOKEN`) |
| Supabase database is temporarily unreachable | Database call raises connection error; handled gracefully | `500 Internal Server Error` (`INTERNAL_SERVER_ERROR`) |

## 8. Out of Scope

- ❌ Role-based authorization dependencies (e.g., `require_role("merchant")` or `require_role("logistics")` — to be added in respective domain feature specs).
- ❌ Token refresh mechanism (`/auth/refresh`) — tokens are valid for the configured expiration period (`jwt_expiration_minutes`).
- ❌ Token revocation / blacklisting (stateless JWTs).
- ❌ Profile update endpoints (`PUT /api/v1/auth/me` or password updates).
- ❌ Frontend UI components or pages (handled in Specs 004, 005, and 006).

## 9. Constitution Compliance

- ✅ **§4.1 Strict Backend Separation**: All authentication verification, token decoding, and database lookups reside entirely within FastAPI.
- ✅ **§4.2 Custom Authentication**: Verifies custom JWTs signed by FastAPI; does not rely on Supabase Auth.
- ✅ **§4.2 Cookie-Based JWT**: Evaluates the `kalano_token` httpOnly cookie as primary credential source, with Bearer header fallback.
- ✅ **§4.3 API Communication**: Endpoint is prefixed with `/api/v1/auth/me`, categorized under tag `Auth`, and specifies typed Pydantic models for responses and errors.
- ✅ **§4.4 Standard Error Envelope**: All 401 exceptions return the standard `{"error": {"code": "...", "message": "..."}}` envelope.
- ✅ **§5 Database Schema**: Queries the existing `users` table schema by `id` without modifying table structure.
- ✅ **§7 Naming Conventions**: Uses `snake_case` for Python dependencies (`get_current_user`, `decode_access_token`) and `kebab-case` for URL paths (`/api/v1/auth/me`).
- ✅ **§14 Testing**: Mandates full Pytest coverage for valid cookie, valid header, missing token, expired token, invalid token, and missing user.
